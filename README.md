# 自走棋对战系统

这是《计算机程序设计基础（2）》课程设计的第一版程序。项目使用 C++03 编写，目标编译环境为 Visual Studio 2008，采用控制台菜单完成人类玩家与 AI 的自走棋对战。

程序不使用 `vector`、`map`、`std::string`、`algorithm` 等 STL 容器与算法，所有集合均由定长数组管理。为方便最终提交，全部源代码集中在一个 `.cpp` 文件中，但内部仍按照类和功能模块组织。

## 项目文件

```text
大作业/
├── AutoChessSystem.cpp                       全部 C++ 源代码
├── AutoChessSystem.exe                       本地编译生成的可执行文件
├── test_cases.txt                            文件测试输入
├── test_results.txt                          文件测试输出，由程序覆盖生成
├── README.md                                 项目结构与使用说明
├── 2026程设2大作业任务书-自走棋对战系统.docx  课程设计任务书
└── 示例.docx                                 报告格式示例
```

提交或移动程序时，至少应保留：

- `AutoChessSystem.cpp`
- `test_cases.txt`
- `README.md`

`test_results.txt` 会在运行文件测试时自动创建或覆盖。`AutoChessSystem.exe` 是构建产物，可以重新编译生成。

## 功能概览

- 玩家对战 AI。
- 6×6 棋盘自动战斗。
- 商店购买、刷新和出售棋子。
- 棋子上阵和位置调整。
- 三个同名同星棋子自动合成为更高星级，最高三星。
- 战士、射手、法师、圣骑士四种职业及不同技能。
- AI 自动购买、合成和布阵。
- 从文本文件读取测试阵容，并将测试结果写入文件。
- 对非法菜单输入、金币不足、阵容已满和重复占位等情况进行检查。

第一版没有实现本地双人、AI 对 AI、游戏存档、装备、羁绊、障碍物、联网或图形界面。

## 程序结构

### 类关系

```text
GameSystem
├── Player
├── AIPlayer : Player
├── Shop
├── Battlefield
├── FileManager
└── ChessPiece（抽象类）
    ├── WarriorPiece
    ├── ArcherPiece
    ├── MagePiece
    └── PaladinPiece : WarriorPiece, HealingTrait
```

### 主要类职责

| 类 | 主要职责 |
|---|---|
| `ChessPiece` | 棋子抽象基类，保存公共属性，定义寻敌、技能、符号和优先级等纯虚函数 |
| `WarriorPiece` | 近战、高防御，积累怒气后发动范围重击 |
| `ArcherPiece` | 远程攻击，每三次攻击触发一次确定性暴击 |
| `MagePiece` | 积累魔法值，释放范围伤害 |
| `HealingTrait` | 封装治疗量、治疗范围、冷却和治疗目标选择 |
| `PaladinPiece` | 多重继承战士和治疗特性，能够攻击、治疗和获得护盾 |
| `Player` | 管理生命、金币、棋子所有权、购买、出售、布阵和三合一 |
| `AIPlayer` | 继承玩家类，负责分阶段购买、自动出售、商店刷新和均衡阵型布置 |
| `Shop` | 使用内置定长数组保存棋子目录，生成五个商店槽位并创建派生类对象 |
| `Battlefield` | 管理棋盘、行动顺序、移动、攻击、技能调用和胜负判断 |
| `FileManager` | 读取 `test_cases.txt` 并写入 `test_results.txt` |
| `GameSystem` | 显示菜单并协调商店、玩家、AI、战场和文件测试 |

`ChessPiece` 使用纯虚函数和虚析构函数实现运行时多态。`PaladinPiece` 同时继承 `WarriorPiece` 和 `HealingTrait`，用于展示多重继承。

程序实现了以下运算符重载：

- `operator==`：判断两个棋子能否参与三合一。
- 前置 `operator++`：执行棋子升星。
- `operator<<`：统一输出棋子详细信息。

### 内存所有权

- `Player` 和 `AIPlayer` 是棋子对象的唯一所有者。
- 棋子通过 `new` 创建，通过所属玩家的析构函数、清空或出售操作释放。
- `Battlefield` 只临时保存棋子指针，不释放棋子。
- `ChessPiece` 具有虚析构函数，可以通过基类指针安全删除派生类对象。

## 编译方法

### Visual Studio 2008

1. 新建一个 Win32 Console Application（Win32 控制台应用程序）。
2. 选择空项目，或删除模板自动生成的源文件。
3. 将 `AutoChessSystem.cpp` 添加到项目的 Source Files 中。
4. 如果项目启用了预编译头，在项目属性中关闭预编译头，或为该源文件设置“不使用预编译头”。
5. 编译并运行项目。
6. 若要使用文件测试，确保运行时工作目录中存在 `test_cases.txt`。

VS 2008 的调试工作目录通常是项目目录。如果测试文件与项目文件不在同一目录，可以：

- 将 `test_cases.txt` 复制到项目目录；或者
- 在“项目属性 → 配置属性 → 调试 → 工作目录”中设置为本项目文件所在目录。

当前环境没有安装 Visual Studio 2008，因此没有直接使用 VS 2008 编译；源码已限制在 C++03 语法和 VS 2008 可支持的标准库范围内。

## 使用说明

### 主菜单

```text
1. Start Human vs AI
2. Instructions
3. Run file tests
0. Exit
```

- 输入 `1` 开始一局人机对战。
- 输入 `2` 查看游戏内英文说明。
- 输入 `3` 读取测试文件并生成测试结果。
- 输入 `0` 退出。

菜单使用英文 ASCII 文本，以避免 Visual Studio 2008 在不同系统代码页下出现中文乱码。

只读展示页面使用 `*** Title ***` 表头；需要玩家继续选择的交互菜单和列表使用 `--- Title ---` 表头。

选择 `Show shop` 或 `Buy piece` 时，程序会在 Shop 表头下方先显示一行玩家当前状态，再显示商品列表。该状态行不带 `Human Status` 表头。

### 准备阶段

```text
1. Show status and roster
2. Show shop
3. Buy piece
4. Refresh shop (2 gold)
5. Sell piece
6. Place or move piece
7. Return piece to bench
8. Finish preparation
0. Abandon game
```

推荐操作顺序：

1. 查看商店。
2. 购买至少一个棋子。
3. 选择 `Place or move piece`，将棋子放到第 4～5 行。
4. 根据需要继续购买、刷新、出售、调整阵型，或选择 `Return piece to bench` 将已部署棋子移回板凳。
5. 确保至少有一个棋子上阵，然后选择 `Finish preparation`。
6. AI 自动完成准备，随后进入自动战斗。

所有坐标均从 `0` 开始：

- 行号和列号范围均为 `0～5`。
- AI 初始部署区域为第 `0～1` 行。
- 玩家部署区域为第 `4～5` 行。

每次显示 `Human Roster` 后，程序都会输出一个不带额外表头的 6×6 玩家棋盘。棋盘只显示当前已上阵的玩家棋子，板凳棋子仍只显示在 Roster 列表中，AI 棋子不会出现在该棋盘中。

### 棋盘符号

| 符号 | 职业 |
|---|---|
| `W` / `w` | Warrior，战士 |
| `A` / `a` | Archer，射手 |
| `M` / `m` | Mage，法师 |
| `P` / `p` | Paladin，圣骑士 |

大写符号属于玩家，小写符号属于 AI，`.` 表示空格。

## 游戏规则

- 玩家和 AI 初始生命均为 30，初始金币均为 10。
- 每个新回合双方获得 5 金币。
- 商店每次显示 5 个棋子，手动刷新消耗 2 金币。
- 每方最多持有 10 个棋子，最多同时上阵 6 个棋子。
- 三个同名、同星棋子会自动合成，最高为三星。
- 战斗按照速度从高到低行动，排序使用手写选择排序。
- 棋子优先选择曼哈顿距离最近的敌人；不在射程内时向目标移动一步。
- 基础伤害为“攻击力－防御力”，最低造成 1 点伤害。
- 单场战斗最多进行 100 个行动轮次。达到上限时判为平局，双方各扣 2 点生命。
- 初始棋盘打印后停留 2000 毫秒，之后每轮棋盘打印后停留 1000 毫秒，方便观察战斗过程。
- 战败方受到 `2 + 敌方存活棋子星级总和` 点玩家生命伤害。
- 任意一方玩家生命降至 0 时整局游戏结束。

### AI 购买与布阵策略

AI 只根据自己的阵容、金币和当前商店进行确定性决策，不读取玩家阵容。Warrior 和 Paladin 视为前排，Archer 和 Mage 视为后排。

- 基础阵容阶段优先凑足 6 枚棋子，并保证至少拥有 2 名前排和 2 名后排。购买判断会预估自动合成造成的棋子数量变化，补阵容时优先选择价格更低的合适商品。
- 阵容成形后依次追求即时合成、主力职业对子、同角色高价值替换和未三星主力的后续升星；不购买与主力无关的一星散件。
- 当前商店没有合适商品且金币不少于 4 时，AI 每回合最多刷新一次，确保支付 2 金币后仍有机会购买最低价棋子。
- 持有数量达到 10 时，AI 只会出售不属于主力六人、没有对子关系且不会破坏最低前后排数量的一星散件；不会出售高星棋子或拆散对子。
- 主力六人先选择价值最高的 2 名前排和 2 名后排，再以“星级 × 1000 + 价格 × 100”补足剩余位置。前排部署在第 1 行，后排部署在第 0 行。

## 文件测试

在主菜单中输入 `3`，程序会：

1. 从当前工作目录读取 `test_cases.txt`。
2. 按文件内容创建玩家和 AI 阵容。
3. 静默运行自动战斗。
4. 将结果写入或覆盖 `test_results.txt`。

### `test_cases.txt` 格式

文件只接受以空白字符分隔的整数，不要添加文字注释。

第一行：

```text
测试用例总数
```

每个测试用例的头部：

```text
预期胜者 玩家棋子数 AI棋子数
```

随后先写玩家棋子，再写 AI 棋子，每个棋子一行：

```text
职业编号 星级 行 列
```

编号定义：

| 字段 | 数值含义 |
|---|---|
| 预期胜者 | `0` 玩家胜，`1` AI 胜，`2` 平局 |
| 职业编号 | `1` 战士，`2` 射手，`3` 法师，`4` 圣骑士 |
| 星级 | `1～3` |
| 行、列 | `0～5` |

例如：

```text
1
0 1 1
1 2 4 1
2 1 0 3
```

含义为：共有一个测试用例，预期玩家获胜；玩家有一个位于 `(4,1)` 的二星战士，AI 有一个位于 `(0,3)` 的一星射手。

### `test_results.txt` 格式

```text
Case Expected Actual Rounds Status
```

- `Expected`：测试文件中的预期胜者。
- `Actual`：程序计算出的实际胜者。
- `Rounds`：该场战斗使用的行动轮次。
- `Status`：预期与实际相同为 `PASS`，否则为 `FAIL`。

当前自带的三组测试结果均为 `PASS`。

## 已知限制与后续扩展

- 当前仅支持玩家对战 AI。
- AI 使用固定、确定性的分阶段购买和均衡布阵规则，不会针对玩家阵容动态调整。
- 移动采用简单的曼哈顿距离贪心策略，没有障碍物和复杂寻路。
- 棋子目录直接写在 `Shop` 类中，不从外部配置文件读取。
- 没有保存和读取游戏进度。
- 控制台战斗详细模式会在每个行动轮次输出棋盘，并加入固定观看延迟；文件测试不受延迟影响。

后续可以在不改变棋子基类和战场核心接口的前提下增加本地双人、AI 对 AI、存档、更多职业或图形界面。
